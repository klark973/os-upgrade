# Разработчику дистрибутива

## Стадии обновления

Утилита (она же демон) выполняет обновление поэтапно, одну стадию за другой.
Прохождение стадий, число перезагрузок, выполнение в тех или иных таргетах
systemd, зависит от исходного состояния системы и параметров запуска утилиты.
По умолчанию предполагается следующая цепочка выполнения:

`CHECKS` -> `START` -> ... -> `DEINIT` -> `CLEANUP`.

* `CHECKS`: Проверяет все необходимые условия и возможность обновления.
  На данном этапе регулярный журнал не ведётся и демон ещё не запущен,
  фатальные ошибки попадут в stderr (по умолчанию при автозапуске из `%post`
  они попадут во временный журнал `/var/log/os-upgrade-err.log`). Для каждого
  бранча, с которого предусмотрено обновление поддерживаемого дистрибутива,
  должен иметься соответствующий данной стадии скрипт `<branch>/checks.sh`
  с функцией `check_<branch>()`, см. следующий раздел.
* `START`: Определяет начальное состояние ряда сервисов, копирует скрипты
  os-upgrade в `/usr/local/libexec`, исправляет некоторые известные проблемы
  уже развёрнутых систем ОС Альт, готовит регулярный журнал, каталог состояния
  демона (`/var/lib/os-upgrade`) и запускает сервис обновления. На самом деле
  название данной стадии выбирается по умолчанию, его можно переопределить
  в функции `check_<branch>()` присвоением в переменную `stage=...`.
* Все поддерживаемые целевые обновления должны содержать скрипты для стадий
  `CHECKS` и `START`. Все остальные стадии могут называться произвольно, их
  число не регламентировано. Скрипты всех стадий, начиная со `START`, должны
  определять хотя бы одну функцию: `run_stage()`, ей передаётся управление
  при переходе к данной стадии. Каждый скрипт по окончанию работы определяет
  название следующей стадии. Выполнение демона завершается, если следующая
  стадия называется `FINISHED`. Рекомендуется завершать цепочку переходом
  к стадии `DEINIT`, описанной далее.
* `DEINIT`: Восстанавливает состояние ряда служб, завершает работу сервиса
  os-upgrade и запускает скрипт окончательной очистки. При этом следующая
  стадия устанавливается в `FINISHED`, а скрипт очистки работает в фоновом
  режиме уже после остановки сервиса.
* `CLEANUP`: Удаляет все оставшиеся файлы пакета, кроме журнала обновления.

См. также [эталонную реализацию обновления](/usr/libexec/os-upgrade/c10f1/).

## Определение поддерживаемого обновления

В каталоге бранча (`/usr/libexec/os-upgrade/<branch>`), с которого будет
выполняться обновление, должен содержаться скрипт `checks.sh` с функцией
`check_<branch>()`. Она должна возвращать 0, если обновление обнаруженного
решения поддерживается. Рекомендуется сразу выставлять начальное значение
переменной `stage`, отличной от умолчания.

Используйте префиксы для отличий цепочек шагов-стадий между различными
дистрибутивами. Например, пусть дистрибутиву «Альт Рабочая станция 10»
соответствует префикс «ws-». Тогда скрипты стадий в подкаталоге `p10/`
могли бы называться так: `ws-start.sh`, `ws-prepare.sh`, `ws-upgrade.sh`,
`ws-finalize.sh`, `deinit.sh`, последний можно сделать симлинком на уровень
ниже. И тогда не возникнет конфликтов, если со временем в том же каталоге
появятся файлы с префиксом «sl-» для обновления с «Simply Linux 10».

## Значения по умолчанию

* Глобальные значения: описаны в самом начале
  `/usr/libexec/os-upgrade/main.sh`, а также в
  `/usr/libexec/os-upgrade/defaults.sh`;
* Для конкретного бранча: добавляются в
  `/usr/libexec/os-upgrade/<branch>/defaults.sh` вместе с парой функций:
  `load_<branch>_data()` и `save_<branch>_data()`, если необходим перенос
  значений между перезагрузками через каталог состояния демона.

## Наиболее полезные функции

* `msg()`: Вывод сообщения для пользователя. См. также другие функции
  `msg_XXXX()` в `common.sh`, например, `msg_bold()` или `msg_fail()`.
* `next_stage()`: Определить название следующей стадии. С префиксом `-n`
  будет означать, что переход к этой стадии должен произойти без перезагрузки
  (no-reboot). Обратите внимание: в скриптах и в файловой системе используются
  прописные, заглавные выводятся только в журнал и упоминаются в документации.
  То есть, стадии «WS-UPGRADE» будет соответствовать скрипт `ws-upgrade.sh`,
  в скрипте это будет выглядеть как `next_stage [-n] ws-upgrade`.
* `next_target()`: Определить название дефолтного таргета systemd при следующей
  загрузке системы либо (с `--restore`) восстановить дефолтный таргет systemd,
  который был установлен при запуске утилиты.
* `will_run()`: Выводит команду в лог, но не выполняет её. Обычно используется
  перед выполнением той же команды, когда её вывод stderr необходимо подавить
  или перенаправить куда-то ещё.
* `run()`: Выполняет указанную команду, выводя её перед этим в журнал.
* `try()`: Выполняет заданное число попыток вызвать указанный callback.
  В случае n=0 число попыток будет бесконечным. После каждой неудачной попытки
  пауза перед следующей попыткой удваивается. Таким образом, обеспечивается
  механизм выполнить что-либо (например, скачать пакеты) с нескольких попыток.
* `fatal()`: Может использоваться на ранних стадиях в `checks.sh` для фатального
  выхода из программы, но лучше так не делать, а возвращать ненулевое значение.
* `su_fatal()`: Используется, в основном, этот вариант фатального завершения
  работы утилиты и демона, т.к. корректно обрабатывается каталог состояния,
  отключается сервис os-upgrade, а также используется регулярный журнал.
* `su_exit()`: Используется для корректного завершения демона с указанным
  кодом состояния, либо (с `--reboot`) для перезагрузки ОС между стадиями.
  Обычно для перехода на следующую стадию достаточно выйти из `run_stage()`.

См. также [common.sh](/usr/libexec/os-upgrade/common.sh).

## Почему «из кармана», а не штатная установка из репозитория?

Опакечивание набора скриптов обновления системы выполнено для удобства и для
автоматизации их доставки на целевую машину. Инструментарий пакетной установки
нужен только для этих целей, но входящие в пакет скрипты обновления должны
учитывать текущее состояние разных бранчей, а в некоторых случаях самоудаляться
по окончанию обновления. Тут же одна из причин, почему не все каталоги
принадлежат пакету: они создаются на время работы демона и подлежат удалению
уже после удаления пакета, который иногда удаляется в процессе обновления.

Установка произвольного пакета из репозитория со всеми зависимостями обычно
предполагает предварительную настройку источников APT, обновление индексов,
а при включенной защите IMA/EVM потребуется её предварительное отключение.
Столько ручных манипуляций для выполнения процедуры, которую автоматизирует
данная программа! «Карман» здесь решает известную проблему «курицы и яйца». На
текущем состоянии бранча может быть заведомо известно, что возникнет определённая
проблема при установке программы штатным способом из репозитория, тогда как
при установке «из кармана» её всегда можно будет «обойти».

Если столь «особый» пакет предназначен только для разовой операции, вообще
нет смысла постоянно держать его в системе, равно как и в стабильных бранчах.
Пакет может находиться в Сизифе, чтобы не потерялся и нормально поддерживался,
но сразу после бранчевания должен удаляться из стабильного репозитория, чтобы
даже не было возможности устанавливать его иным способом.

## Предлагаемый workflow создания поддерживаемого обновления

* Клонируете к себе git пакета os-upgrade из Сизифа;
* Создаёте подкаталог в `$libdir` для исходного бранча, если его там ещё нет;
* В этом подкаталоге создаёте все необходимые файлы, с учётом сказанного
  выше о префиксах, `checks.sh` и `defaults.sh`, по необходимости;
* Также желательно добавить соответствующий обновлению README в подкаталог
  `/doc/` (в раздел документации);
* Собираете тестовый таск для исходного бранча и тестируете (сами или QA);
* После успешного тестирования таска для бранча отправляете новую версию
  в Сизиф;
* Лидер проекта включает вас в ACL пакета, если вас там ещё нет;
* Маинтейнеры из списка ACL получают уведомление о новой версии в Сизифе;
* Проверенный «карман» передаётся пользователям и защищён от регрессий.


Удачи! ;-)
